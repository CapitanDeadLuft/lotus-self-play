## 2. Данные и метод измерения

Что есть в логах:

- `[fsl]` (host.log.fsl) — раз в ~10 с координаты 4 союзников (включая SK), их planner-роль,
  lane, settled; координаты **Treant в этой строке не пишутся** (5-й герой — сам бот).
- `[SelfPlay] … pos=x,y` (self_play.log.fsl) — координаты Treant на каждом решении (~2.8 с),
  режим (`mode=`), `cast=`, `order=`, `attacks=`.
- `[SelfPlay score]` (раз в 60 с) — `lastHits/denies/xp/networth/heroDamage/laneGold`.
- `[SelfPlay last hit]` — решения `lastHit.plan`: цель, hp/damage/events, `approach`, `inRange`.
- `[SelfPlay last hit stats]` (раз в 60 с) — «N вражеских крипов умерло рядом (M в reach) →
  ours / our creeps-tower / ally heroes / enemy heroes»; `reach = attack range + bonus + 200`.

Чего нет: **координат крипов** — ни в одном логе архива (проверен весь `host.log.fsl`:
`pos=` есть только в 87 строках `[fsl]`, 15290 строк `[entity]` — только счётчики, `[ev]` —
без позиций; в `r11_stages.log` — стадии рендера). В эталонном логе нет и позиций союзников
(только `pos=` самого Treant), поэтому и для S26 прямой «SK→крип» невосстановим.

Отсюда три измеримых величины:

1. **d(SK, Treant)** — точная: ближайший по clock сэмпл `[fsl]` (|dt| ≤ 6 с) к каждому
   `[SelfPlay] pos` (248 пар за матч).
2. **d(Treant, крип)** — на каждом решении: при `inRange=true` цель ≤ attack range
   (+халл), т.е. ~≤200/≤350 (консервативно); при `inRange=false` восстанавливается из
   `approach`: `d ≈ approach·speed + range − 35` (speed 285/300/325, range 150).
3. **Окно у волны** — счётчик `in reach` из `last_hit.stats`: столько вражеских крипов
   умерло в ≤350 от Treant; если в этот момент `d(SK,Treant) < 850`, то для любого такого
   крипа `d(SK,крип) ≤ d(SK,Treant) + 350 < 1200` — гейт **доказуемо закрыт**.

Ограничение: `[fsl]` шаг 10 с, поэтому «доказуемо закрыт» относится к сэмплам, а не к
каждому тику; полноценный ответ даёт только зонд `[gate2]` (§7).

Независимая проверка: `ref-auditor` пересчитал все приведённые числа **отдельным** парсером
(без использования `tools/layer2_fsl.py`) — расхождений >10% нет, все контрольные точки
сошлись (`archive/20261123_fsl/verify_ref.txt`). Аудит фикса и его ограничений —

## 5. Диагноз слоя 2: два лимитера

### 5.1 Гейт `canLastHit` — доказанный лимитер в окнах «ядро в волне»

Цепочка (все звенья — оригинальный код, скрипты не менялись):

1. `self_play/lane_rules.lua:16–21` — `canLastHit` возвращает **false**, если любой союзник
   с planner-ролью ≤3 удалён от **крипа** менее чем на **1200**. У нас такой союзник — SK
   (role=3), он стоит в lane 1 весь матч (`[fsl] set=1`).
2. `self_play/last_hit.lua:532` — в `plan()` вражеский крип попадает в кандидаты **только**
   при `canLastHit == true`; денаи (`denyable`) проходят мимо гейта. Итог: 12 из 13 решений —
   денаи, вражеских кандидатов почти нет. `:611` (execute) и `:712` (`yieldCore`) —
   та же проверка, поэтому начатая атака по вражескому крипу ещё и отменяется.
3. `Self Play.lua:1528` — выбор цели позиционирования: для role ≥4 берутся только денаи
   (`allied and fraction < 0.5`), потому что вражеские отфильтрованы гейтом; далее бот идёт
   в `positioning.lane`/`laneAnchor` (`Self Play.lua:1536–1540`, режим
   `Support lane: deny and protect`). Получается **самоподдерживающийся контур**: целей-денаев
   нет → стоим у волны рядом с ядром → SK в 1200 от крипов → гейт закрыт → вражеских целей нет.
4. Гейт распространён шире ластхитов: `combat.lua:536` (абилочный фарм), `map_farm.lua:94,151`
   (фарм волн по карте) — всё это для role≥4 с ядром рядом тоже отключено.

Доказательства именно для гейта (§3):

- 12/13 решений — денаи (92%), у S26 — 6/25 (24%);
- в окнах, где SK в 49–284 от Treant (clock 336, 339–351, 564), `d(SK,крип) ≤ ~554` →
  гейт закрыт, `in reach`-смерти есть, ours/LH = 0;
- единственное вражеское решение (9:46) появилось при `d(SK,крип) ≈ 1200–1250` — ровно на
  пороге гейта; после 10:59 (SK в 4.9–7.0k) — добивания осадных крипов;
- у S26 партнёр — support (`nyx_assassin`), гейт выключен → 19 вражеских решений и LH 12.

### 5.2 Второй лимитер: покрытие предсказания (`ledger/noFlag`) — виден, но архивом не доказан

Проверка «а всегда ли виноват гейт» даёт важную поправку:

- **8 из 12 денай-решений** приняты при `d(SK,Treant) = 4864–7878` (clock 186/210/214/674/678/681/684/687),
  т.е. `d(SK,крип) ≥ ~4200` — гейт **доказуемо открыт**, и всё равно кандидатов-врагов нет.
- В окнах 180–240 и 360–420 с (гейт открыт) есть `in reach`-смерти вражеских крипов
  (2 и 3), но конверсия 0.
- Значит ворота кандидатов режет ещё и условие «созрел для удара»:
  `last_hit.lua:540` — `health < minimum*2 or #events > 0`, где `#events` — покрытие
  `ledger` (предсказание входящих ударов по крипу). Это ровно второй лимитер из
  `docs/KNOWN_ISSUES.md` AI-20 («матч B»: `gateBlocked=0`, отказы `noFlag` 2–7 за тик,
  покрытие ledger ~54% по `addedHits`).

Архив в текущем виде **не позволяет разделить вклады двух лимитеров**: нет координат крипов
(нельзя посчитать `d(SK,крип)` на каждом отказе) и нет счётчиков причин отказа. Отсюда запрет
на немедленный фикс (`PORT_PLAN.md §1`: «без доказательства — не чиним»): сначала зонд.

### 5.4 Что это не

`lane_choice` тут не при чём (паритет свичей доказан в `FREESUPPORT_2026-11-23.md`), и это не
дефект порта: уступка ядру в 1200 — поведение оригинала (AI-20). Вопрос — **политика**:
она не различает «ядро реально забирает крипа» и «ядро стоит в 1100 и не участвует», а цель

ядре-партнёре.

## 6. Фикс слоя 2: staged-план

Порядок обязателен: сначала измерение, потом минимальная правка в `src/`, потом A/B. Оригинал

### 6.1 Stage 1 — read-only зонд `[gate2]` (делать первым)

Реализация — как у зонда `[fsl]` (прецедент: `archive/20261123_fsl/bot_loop_run.lua.fsl_probe:90–244`),
но из `src/` (не перезаписывается клиентом): новый файл `src/lane_gate_probe.lua` + одна строка
`pcall(require, "lane_gate_probe")` в `src/bot_loop_run.lua` после `loader.load()`.

Зонд оборачивает `self_play.lane_rules.canLastHit` и **ничего не меняет** в результате:

- вызывает `orig(ctx, creep)`; если вернулось `true` — только считает счётчик (для инварианта
  `newYield ⊆ oldYield`); если `false` — инспектирует вход гейта:
  `pos = Entity.GetAbsOrigin(creep)`, `myD = ctx.distance(ctx.position, pos)`;
  по каждому союзнику с role ≤3 (те же guards, что в оригинале) — `dCore`, `reach =
  NPC.GetAttackRange(ally)+GetAttackRangeBonus(ally)+150`;
- считает `flip0` = «при contest-правиле `(dCore <= reach or dCore <= myD)` гейт бы открылся»
  и `flip250` (с запасом 250) — обе цифры нужны, чтобы выбрать порог;
- гистограмма `dCore` по корзинам 0–300/300–600/600–900/900–1200/≥1200 + `myD`, имя ядра;
- раз в 60 с в лог: `[gate2] clock= calls= blocked= flip0= flip250= medCore= minCore= medMe=
  bands=…/…/…/…/…`; окна с flip — до 10 строк `[gate2 row]` (creep, core, dCore, myD, reach);
- плюс обёртка `lastHit.plan` → `[gate2 plan] cand= enemy= allied= none=` раз в 60 с;
- всё в `pcall`, без мутаций `ctx`, без приказов; после ошибки зонд выключается (как `[fsl]`).

Решающие показатели: `flip0/flip250` в окнах 0–600 (и отдельно 0–300), распределение `dCore`
по корзинам, доля отказов с открытым гейтом (`dCore ≥ 1200`) — это и есть `noFlag`-часть.

### 6.2 Stage 2a — contest-aware `canLastHit` (только если Stage 1 подтвердил вклад гейта)

> **Отклонено 2026-11-23 (вечер):** правка не внедряется — `canLastHit` оставлен
> эталонным, см. §10 и `ACCEPTANCE_2026-11-23.md §10`. Раздел сохранён как история.

Вариант **b0** (по итогам аудита `verify_fix.txt`): уступать только если ядро **достаёт
крипа** или **ближе к нему, чем мы**:

```lua
-- reference-реализация правила (в src-override, не в оригинале):
local position = Entity.GetAbsOrigin(creep)
local ownDistance = ctx.distance(ctx.position, position)
if not ctx.runeRoles then return false end   -- нечего проверять -> как в оригинале (уступаем)
for _, ally in ipairs(ctx.allies) do
    local role = ctx.runeRoles[Entity.GetIndex(ally)]
    if ally ~= ctx.hero and role and role <= 3 and Entity.IsAlive(ally) and not Entity.IsDormant(ally)
        and Entity.IsSameTeam(ctx.hero, ally) and not NPC.IsIllusion(ally) and not NPC.IsMeepoClone(ally)
        and Hero.GetReplicatingOtherHeroModel(ally) == nil then
        local coreDistance = ctx.distance(Entity.GetAbsOrigin(ally), position)
        local range = NPC.GetAttackRange(ally)
        if not range or range <= 0 then
            if coreDistance < 1200 then return false end          -- fallback: старое правило
        else
            local reach = range + (NPC.GetAttackRangeBonus(ally) or 0) + 150
            if coreDistance <= reach or coreDistance < 1200 and coreDistance <= ownDistance then return false end
        end
    end
end
```

Отличия от первой редакции (учтено аудит `verify_fix.txt`):

- **без порога +250**: `coreDistance <= ownDistance` вместо `+250 < ownDistance` — иначе
  разрешался прямой контест с ядром (R15);
- **fallback при `GetAttackRange == 0`** — вести себя по старому правилу `< 1200` (R5);
- менять **только последнее условие**, не переписывая цикл guard'ов (иллюзии/Meepo/Arc Warden);
- `ctx.distance` принимает Vector — используем `position`, а не userdata `creep` (R3).

Реализация — **не правка оригинала**, а `src/lane_gate_ab.lua`, который после `loader.load()`
подменяет `require("self_play.lane_rules").canLastHit`; режим из `configs/lane_gate.ini`
(`mode=off|on0`, default `off`), `off` — возврат оригинала без единого лишнего API-вызова
(байт-в-байт паритетное поведение). В обёртке — `clock >= 600 → return orig(...)`: мид-гейм
`map_farm`/`combat.farm` остаются на строгом гейте (R10/R11); функционально это
«только лейн-фаза last hit». Ограничение фиксируется: после 10 мин поведение = эталон.

### 6.3 Stage 2b — если зонд показал доминирование `noFlag`

Тогда правка гейта инертна (whack-a-mole), и следующая задача — покрытие `ledger`

### 6.4 Stage 2c — если конверсия выросла, а `in reach` остался низким

### 6.5 Ожидаемый эффект (честные диапазоны)

- гейт открывает кандидатов только там, где `dCore ∈ 300–1200`; по данным §3 такие окна
